# Android ARMv7 GLES startup (experimental)

The ARMv7 Android host selects `Backends::GL` by default. wgpu's `gles` feature must be enabled specifically for that target; `port/tools/test_renderer_features.py` verifies the resolved ARMv7 and ARM64 graphs in CI. This only establishes that the backend is compiled.

The renderer's native shaders load depth textures with `textureLoad`. Naga 29's GLSL writer rejects that operation. The local `vendor/naga` fork maps raw depth loads to `texelFetch` of a non-shadow sampler and selects `.x`; it fails closed for depth sampling operations, which the renderer does not currently use. This is an application-specific GLES workaround, not a general replacement for Naga's shadow-sampling support. Mesa GLES tests initialize the renderer and read back four depth values (0, .25, .75, 1); they do not validate all texture dimensions, driver behavior, or the complete game.

GLSL ES lacks core `noperspective`. For the native shader only on the GL backend, two linear varyings are compiled as perspective varyings: its vertex position is explicitly written with constant clip-space w=1, making the interpolations mathematically equivalent. The GLES smoke test checks that invariant and the exact varying declarations. Changes to the shader's vertex w or interpolation declarations must revisit this workaround.

The Linux test forces a Mesa GLES rather than desktop GL context using the Linux-only, test opt-in `DHD_TEST_FORCE_GLES`. It covers software-renderer startup, representative pipelines and depth readback. It does not test Android's EGL window, the phone's PowerVR driver, performance, rendering accuracy, gameplay or the previously observed RenderThread SIGSEGV. Real-device logs and testing remain mandatory; a green CI is not a playable-release claim.

## PowerVR compute constructor (4d83fcc phone log)

On Xiaomi 23028RN4DG the adapter successfully initialized as `PowerVR Rogue GE8320`, OpenGL ES 3.2; exact pipeline `main` then failed driver compilation with `ERROR: 0:1200: 'constructor' : too many arguments`. A locally generated Mesa ES 3.2 version of the same default pipeline places a nested `Primitive(uvec4[3](...), ...)` constructor exactly at line 1200, a strong candidate but not proof the device-generated source is identical. The GLES writer now initializes locals with structs containing arrays through explicit zero assignments rather than nested constructors, preserving WGSL initialization. Desktop GLSL remains unchanged. CI compiles all eight exact raster keys on Mesa GLES and checks generated ES 3.1/3.2 and desktop GLSL; a negative control rejects the old nested constructor. It also reads back representative nested zero-initialized fields. A bounded GLSL excerpt around reported line numbers is logged on compilation errors for phone-side diagnosis. Tests do not reproduce the PowerVR compiler; hardware testing remains necessary.

## PowerVR fragment invariant and boot diagnostics (9936f85 phone log)

The GE8320 got past the previous exact compute constructor failure and then rejected `invariant gl_FragCoord;` in the native fragment pipeline, explicitly saying only shader outputs can be invariant. GLSL ES code generation now omits this declaration on fragment input while retaining the invariant vertex `gl_Position` output. The existing desktop GLSL path stays unchanged. A regression test translates the actual native WGSL into GLES 3.1/3.2 and desktop GLSL, checks both shader stages, and has an old-writer negative control; Mesa GLES still cannot prove the PowerVR compiler will accept subsequent shaders or boot the game.

The Android-visible `dhd.log` remains one append-only file. Each launch gets a `[NEW LAUNCH]` separator, CI commit/build label, and `[BOOT +seconds]` markers around disc, GPU, exact/native shader compilation, surface readiness, and the first present request. `[CRASH]` markers surround the existing signal/backtrace report. These markers do not prove a frame was visible or gameplay worked. SIGKILL, ANR, failures before logger initialization, and failures of the existing signal handler may leave no crash section; do not treat missing `[CRASH]` as evidence of a clean exit. The log can include device details and the selected content URI.
